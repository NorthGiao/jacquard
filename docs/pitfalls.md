# Pitfalls and constraints (each maps to a lint code or a writer fix)

Rule: **for a newly hit pitfall, if it can be written as a check, put it in `jacq/lint.py` and add a case to `tests/test_lint_pitfalls.py`**; only what has to be remembered by people is written only here.

## 1. Caught by lint (code → symptom → cause)

| Code | Level | Symptom (on-site) | Cause / correct form |
|---|---|---|---|
| `AUTOIDX` | E | VI broken, no further information | Wires leaving a For loop are always auto-indexed (+1 dimension per level passed out); a scalar indicator wired to a source inside the loop is bound to break. For the final value: source → `sr.right`, `sr` outside the loop → indicator |
| `DIMS` / `DIMS?` | E / W | Same as above (failtest `broken`) | Source dimensions + number of For levels passed out must = indicator dimensions. The source's dimensions are inferred by type propagation (function outputs, outputs of this job's subVIs); W only when they can't be inferred |
| `TYPE` | E | VI broken (category pairs confirmed on-site: bool↔num, str↔num, num→cluster, cluster→num, scalar↔array, path↔string, bool↔string, num↔path, clusters with different element counts) | The categories at the two ends are incompatible (indicators, function terminals, the While stop terminal, case selectors, both inputs of Select, merging tunnels all count). The fix is given per category. Sources in the header of `jacq/typecheck.py`, `docs/lint_robustness.md` |
| `TYPE?` | W | (not confirmed on-site) may be broken | Other category mismatches: different enum items, different cluster element types (same count), bool↔path, enqueued element ≠ queue element, differences on Graph indicators. A scalar into a Waveform Chart is not reported (builds on-site) |
| `TYPE-UNK` | I | — | This function has no type rule → wires downstream of it get no type check (`jacq/typecheck.py` `_RULES`; adding a rule needs an on-site source) |
| `REQ` / `REQ?` | E / W | VI broken (Add.y, Select.f unwired: confirmed on-site by typeprobe) | An input without a default value is unwired. Confirmed ones give E, the rest of the table (`typecheck.REQUIRED`) gives W |
| `CASE-DUP` / `CASE-DEFAULT` / `CASE-VAL` (E); those with `?` (W) | E / W | VI broken (typeprobe tp33–tp35) | E: duplicate case values with an integer selector, integer selector without a default case, case values of an enum selector that aren't enum items. W: the same kind of problems with string/bool selectors (not confirmed on-site). Full enum coverage, or bool with both true and false, need no default; integer ranges `"1..3"`, `"5, 7, 9.."` are valid |
| `EXPECT-MISS` | E | — | An E that the job's `LINT_EXPECT` says should be reported wasn't reported = lint regression (used by failtest); I's prefixed with `[EXPECTED]` / `[BUILD_ONLY]` are expected E's that were deliberately downgraded |
| `EXPECT-BAD` | E | — | `LINT_EXPECT` can only downgrade type-related codes that predict "will be broken" (`lint.PREDICTIVE`). E's like terminal names, won't stop, hardware I/O may not be downgraded; change the spec. A job with `LINT_EXPECT` is not recorded as verified even if it passes on-site |
| `SHAPE` | E | Not run on the LabVIEW machine (a constraint of the tool itself: the later checks can't be done) | The shape of spec / tests / runs is wrong: something that should be a list written as something else, a node missing `name`, a structure missing `type`, a subVI's `path` not a string (most common: `OUT / "sub.vi"` forgot `str()`), the value shape of some step in `runs.actions` is wrong (`click` takes a string, `set` takes a dict, `read` takes a list of names, `wait` takes a number), `repeat` not a positive integer. Tuples are reported too: jobs always use lists by convention (the spec's controls / functions / wires etc. get concatenated as lists, and tuples crash there), change it to a list. A VI with the wrong shape isn't checked further, the other VIs are checked as usual |
| `LINT-BUG` | E | — | A form lint itself didn't anticipate: gives an E instead of a traceback. Most likely still a spec shape problem; if it can't be found, report it to the maintainer |
| `HW-IO` | E | `vi_job.py` on the LabVIEW machine refuses the whole job (`JOB COMPLETE REFUSED`) | The job pipeline only builds and runs pure-computation VIs (`lab/jobguard.py`, the same file for lint and the LabVIEW machine). SubVIs are a whitelist (VIs under the output directory `BASE\write2\jobs\<job>` computed from the job name -- not the `OUT` written in the job file itself, see `JOB-OUT` -- or VIs registered in `VILIB_ALLOW` of `lab/jobguard.py` located under vi.lib of the default LabVIEW installation directory); functions are a denylist scanned by palette-name prefix (hardware I/O: VISA / GPIB / Serial / DAQmx...; network: TCP / UDP / HTTP...; external code: System Exec / Call Library Function / Python Node...; dynamically calling other VIs: Open VI Reference / Call By Reference...); VI Server property / invoke nodes using `"class"` (such as Run VI of the VI class) are not allowed. This is a bottom line, not a prediction, and can't be downgraded with `LINT_EXPECT`. Words like serial / visa in the job name or VI name don't matter (only function names and where subVIs are count). Limitation: the function denylist matches by name, hardware functions not on the list slip through -- the fallback is the subVI whitelist and `UNVERIFIED` in strict mode (the learned layer also has hardware functions like `VISA Write`, so terminal-name checks alone aren't enough) |
| `LABEL-DUP` | E | (derived from reading the code, not seen on-site) tests set / read another control, relabel changes the wrong object | The labels of controls + indicators in one VI must all differ: `vi_job` / `vi_test` set and read values by visible label, the writer finds references by label, subVI terminal names = labels. Controls with Chinese labels are first built with `name` as a temporary label, so their `name` may not equal another label either |
| `LABEL-CP` | W | The label becomes `??`, and afterwards the control can't be found by label | The label has characters the LabVIEW machine's code page can't represent (judged by 936, `LAB_CODEPAGE` in `jacq/lint.py`; change it when the LabVIEW machine is not a Simplified Chinese system). The only case seen on-site is Korean turning into `??` under 936 |
| `JOB-NAME` / `JOB-NAME?` | E / W | The LabVIEW machine refuses everything (a VI name with a path would be built outside this job's directory; an invalid job name is refused by the LabVIEW machine before the job is loaded) | The VI name is the file name under `OUT`: empty, containing `\ / : * ? " < > |` or control characters, leading / trailing space / dot, a Windows reserved name like `CON` / `NUL` / `COM1`, more than 100 characters → E; containing non-ASCII characters → W (non-ASCII in file names and subVI paths hasn't been verified on-site). The job name (the file name of `jobs/<job>.py`) may only contain letters, digits, underscores, otherwise E. The two regexes (`jobguard.BAD_VI_NAME`, `jobguard.JOB_NAME`) are shared by lint and `lab/vi_job.py`; VI names may contain hyphens, job names may not |
| `JOB-ARG` | E | Not run on the LabVIEW machine (wrong command-line argument, a constraint of the tool itself: `jacq.run` prints "not run on the LabVIEW machine", `job_check` says one sentence with exit code 2, neither writes any record) | Write the job name as the command-line job argument, or `jobs/<job>.py` (relative paths are resolved against the current directory or the repo root). `x.py` in another directory and `jobs/old/x.py` are both refused, otherwise a different `jobs/x.py` would silently get linted / run on the LabVIEW machine / recorded. The job name may only contain letters, digits, underscores, whether written directly or extracted from the `.py` file name: `x.py.py`, with spaces, with dots (`old.x` would load `jobs/old/x.py`), with slashes (`jobs/x`) are all refused, otherwise the record key and the loaded file wouldn't match. A bare `x.py` without a directory is just the job name `x`, regardless of whether that file exists in the current directory |
| `IMPORT` | E | Not run on the LabVIEW machine (the job file errors as soon as it's loaded: syntax error, a module that can't be imported, `sys.exit(n)` called in the file; loading the same file on the LabVIEW machine would fail too) | First make `python -c 'import jobs.<job>'` pass. The message carries the exception type and original text; `sys.exit(n)` during loading is turned into one sentence and doesn't quietly end with that exit code (same for lint, `job_check`, `oracle`) |
| `AUTOIDX-IN` | I | The result is only right for the first element / wrong number of iterations | An array going directly into a For loop from outside = element by element. For the whole array: `x → s.left`, read `s.left` inside the loop, `s.left → s.right` |
| `FOR-N` | E | Can't be built / undetermined iteration count | A For loop either has N wired, or at least one array auto-indexed in |
| `WHILE-STOP` | E | vi_run waits out the whole timeout | A While loop must have `W.stop` wired (true = stop; with `stop_if_true: false` it's "true = continue") |
| `TERM` | E | 1063 "A wire names a terminal the node does not have" | Terminal name = LabVIEW Context Help label, verbatim (`x >= y?`, `0, 1` with spaces). `python -m jacq.catalog terms <function>` |
| `UNVERIFIED` | E (W offline) | Same as above, needs an extra probe round | For unverified functions first probe them (`scripts/probe_terms.sh`, or the same-machine steps in skill `labview-lab-session`); offline, `--offline` queues them automatically, on-site `--queue` probes them all at once |
| `FUNC?` | E | Misspelled function name, or quotes / `$` / backticks / control characters in the name (queued into the probe queue it would break the command sent to the LabVIEW machine) | lint gives the closest name |
| `BANNED` | E | Some terminals can't be wired by name | `Random Number (0-1)` → wrap `Uniform White Noise.vi` (`randu` in mcpi); `String Subset` → String To Byte Array → Array Subset → Byte Array To String (gallery `substr`) |
| `MULTI` | E | Build fails | An input can only have one source (except case structure output tunnels with one wire per frame) |
| `ARRSTYLE` | E | The array turns into another control | Change the style of array elements with `element_style`; `style` is only for graphs/charts |
| `ZHSUB` / `GEN`(ASCII) | E | **The caller's wires are silently dropped** | VIs used as subVIs don't use Chinese labels on their controls; top-level VIs are free to |
| `GEN` | E | gen.build reports an error | The writer's own validation (names, structure terminals, at least one node...); the error usually already contains the correct form |
| `SUBVI?` | E | SubVI terminals unknown | A subVI is a VI earlier in this job, or in `subvis` of `terminals_confirmed.json` |
| `JOB-OUT` | E | The LabVIEW machine refuses this whole job (`refused`) | `OUT = BASE / "write2" / "jobs" / "<job>"`, must be exactly equal (case-insensitive, `/` and `\` equivalent), not just ending right; the LabVIEW machine only accepts this directory computed from the job name (`jobguard.job_out`), and HW-IO's subVI whitelist is judged by it too |
| `JOB-ORDER` | E | The subVI doesn't exist yet | In VIS, subVIs come before their callers |
| `JOB` | E | Not run on the LabVIEW machine (without these two, none of the checks after lint can be done; the LabVIEW machine also needs them to load the job) | The job file must define `OUT` and `VIS`, written like `jobs/_template.py` |
| `JOB-DUP` | E | (derived from reading the code, not seen on-site) reports, `.spec_hash.json`, `verified.json` are all indexed by VI name, two with the same name overwrite each other | The `name` of each VI in `VIS` is unique |
| `JOB-SUBVI` | E | The file doesn't exist on-site, can't be built (the LabVIEW machine only builds the VIs in VIS under `OUT`, and doesn't create subdirectories; this is a constraint of the tool itself, not a prediction) | Write this job's subVIs as `str(OUT / "<name in VIS>.vi")` (the case of the name and extension must match what's written in VIS: the LabVIEW machine's cache dependencies are identified by this name); pointing to `OUT/nested/…` or a name not in VIS won't do |
| `RUN-CHECK` | E | (derived from reading the code, not seen on-site) `runs.check` is a function name, looked up by name in the job file on-site; without this function there's nothing to call | Define `def check_xxx(values) -> dict` in the job file, with a boolean `"pass"` in the return value, and write `"check": "check_xxx"` in `runs` |
| `RUN-WHILE` | I | The VI has a While loop but `runs` gives no `actions` / `timeout`: if it doesn't stop it waits out the default 120 s | Give `actions` (click the stop button) or `timeout`; if you're sure it stops by itself, ignore this one |
| `TEST-KEY` / `RUN-KEY` / `ACT` | E | The test can't read the value / can't click the button | Jobs always use the spec **name** (vi_job swaps in the visible label); click can only click booleans |
| `ACT-STOP` | W | Waits out the timeout | The last step of a UI test clicks the stop button |
| `NOTEST` | W | "Built" ≠ "correct" | Each VI has at least one tests or runs+check; expected values are computed with a Python reference implementation |
| `RUN-NOCHECK` | W | "Passed" on-site, but nothing was actually asserted | `runs` has no `check`, and the VI has no tests either. The evidence kind of such VIs in `verified.json` is recorded as `runs(no assertion)`. The return value of check must have a boolean `"pass"`, without it `vi_job` judges it not passed |
| `WIRE-UNSUP` | W | All tests pass on-site, but `job_check` doesn't record verified | The spec uses a form the wire check (`jacq/wire_diff.py`) doesn't recognize yet (currently `invoke_nodes`). If the check wasn't done it doesn't count as verified; change the form, or first add support to wire_diff (needs an on-site dump as basis) |
| `UNDRIVEN` / `UNUSED` | W | — | Most likely a missing wire |
| `STOP-ONCE` | E | Pressing the stop button doesn't stop the loop (vi_run waits out the timeout) | Control terminals are placed at the top level, outside the loop by default, and are **read only once before the loop starts**. The stop button must go into an event structure inside the While (a `{"control": "stop"}` frame; the writer automatically moves `[stop, W.stop]` into that frame), or be read via a Value property node inside the loop. Independent of the order the wires are written in |
| `STOP-ONCE?` | W | Same as above, but the loop may stop by itself on some other condition | A boolean control reaches the stop terminal along the wires **via functions, shift registers, tunnels or the `pass` of a case frame** (`stop → Or → W.stop`, the common "stop or error" form; functions count both inside and outside the loop): the button is still read only once. If pressing it should stop, change it as above; if the loop stops on other conditions anyway, ignore it. Going through a case structure's selector doesn't count (that's just `READ-ONCE`) |
| `READ-ONCE` | W (I without an event structure) | Changing the control while running has no effect | Same as above; to read the new value each iteration: put a `{"control": x, "properties": ["Value"]}` read property node inside the loop |
| `LEARNED` | I | Wrong wiring in the first on-site round | The terminal name comes from offline dump pairing (learned layer) and has never been wired on-site; usually trustworthy |
| `STYLE-LINK` | W | Property nodes writing to LEDs/charts in event frames don't work | `lv.py` only does "change style first, then create the node" for controls referenced by top-level property nodes; controls referenced only inside event frames lose the link after the style change. Remove style, or also put a property node at the top level |
| `LATE-ELEM` | W | (not seen on-site) elements wired to the wrong position / 1063 | Property-node wires are drawn in the second pass, and whether `element[k]` of growable functions can be found by position at that point is unverified; put a Select in between |
| `WRITER` | E | Style/default value silently disappears on the VI | Writer regression (the spec has style/default, the generated result doesn't). Not the spec's fault; fix `writer/` |
| `PATHESC` | W | Path test `expected "D:\\\\a" got "D:\\a"` | The test value has two consecutive real backslashes (escaped one level too many when transcribing from `r"D:\a"`). LabVIEW normalizes paths to single backslashes. Write `r"D:\a\b.txt"` |
| On-site `job_check` exit code 2 "no verdict" | Not recording verified | — | When no verdict is possible, the last `====` line says why: the report wasn't produced by the current job (job file / spec changed after the LabVIEW machine run, or the pull-back failed and old results were used), the LabVIEW machine didn't finish that round, `--only` ran only part, some VI is missing a scan dump / the dump isn't from this spec version / the wire check wasn't done / the build isn't confirmed, a result file can't be read, it's an `LVAGENT_FAKE` dry run. None of these is counter-evidence, the old record is not revoked; rerun a round (add `--force` if a dump is missing) |
| On-site `job_check` "front-panel style mismatch" | Not passed | A graph became a numeric array | The writer didn't carry the spec's style onto the VI (e.g. a Waveform Graph built as a numeric array), which neither tests nor the wire check can see → job_check compares the dump's `vi_class`, and a mismatch revokes the verified record |

## 2. Fixed in the writer (`writer/patches/`, verified on-site)

| Symptom | Cause | Fix |
|---|---|---|
| Empty front panel, "did not return the references" | Chinese labels make the whole XML script fail silently. **Root cause**: NI's XML scripting parser parses as UTF-8 and stores the UTF-8 bytes of attribute values into labels as-is, while LabVIEW strings are in the system code page (936/GBK on Simplified Chinese Windows). Raw Chinese (GBK bytes, mostly not valid UTF-8) → the whole script fails; written as `&#22686;` or UTF-8 bytes → the script succeeds but the label is mojibake `澧炵泭`. So **any Chinese** can't be set as a correct label via XML (the GBK bytes of a few characters happen to be valid UTF-8, like "茅", but what gets stored is a different character too) | Build with an ASCII name first, relabel at the end (set as a string via COM, correct) -- don't try encoding workarounds again |
| A graph covers other controls | After a style change the new object doesn't keep its position, with a nonlinear offset | `position` is placed precisely with setpos after the style change |
| The array shows only 1 element | Upstream has no such option | `visible: [rows, columns]` (generates a helper VI that writes NumRows/NumCols) |
| An LED array is square buttons | `style` only changes the top level | `element_style` |
| Event structures with control events are all broken | Upstream's event code table follows LabVIEW 2026; Value Change in 2024 Q1 = 66 | `CONTROL_EVENTS_BY_VERSION` |
| Insert/Replace/Delete Array reports 1063 | The index terminal only appears once array is wired | Index wires go into the second wiring pass |
| Wires to Chinese subVI terminals are lost | Same root cause as "Chinese labels" | Rejected outright (SpecError), lint reports it too |

## 3. Only remembered by people

- Leave at least 10–20 px for the x of `position`: a label wider than its control sticks out to the left, and at x=0 it gets clipped.
- Waveform graph: `dbl[]` = one plot; `dbl[][]` = one per row (assembled with Build Array).
- Array constants used only inside a loop go **inside** the loop (outside, they become an auto-indexed input).
- When `vi_run` and `vi_snapshot` are called separately the VI gets unloaded, and the screenshot shows the initial panel → use the job's `runsnap`.
- In the scan dump, the N of a For loop is reported as class `Tunnel` (real tunnels are `LoopTunnel`) -- wire_diff already handles it.
- The wire check (wire_diff) compares the multiset of (source type.terminal → sink type.terminal): **wrong wiring between two nodes of the same function can't be seen** (swapped terminals like x/y, an unwired frame, wrong wiring between different types can all be seen). The representation of case/event frames is in the header of `jacq/wire_diff.py`.
- Real terminal names in the dump ≠ positional names in the spec: Concatenate Strings reports `string[k]`; Build Array reports `element[k]` with two scalars, and `array`/`element` (without position) when there's an array input -- wire_diff compares by position / wildcard.
- **Review the coverage of checks the agent wrote itself**: e.g. a traffic-light check that only read red and green twice would "pass" even with a wrong yellow light. Before acceptance look at which behaviors the check judges; for timing tasks use `_read_t` to infer the expected state from the measured times.
- Shift registers **can't pass through event structures** (the writer can't do it): for buttons changing state use front-panel controls + property nodes inside the frames (`docs/spec_reference.md` "Button events change state").
- Non-ASCII characters in string constants: the only thing **observed** is Korean `안녕` turning into `??` under code page 936 (upstream test live_vi_edit's "constant values" fails because of it); that Chinese constants survive is an **inference** (936 can represent them), not specifically tested.
- Run parameters picked by feel give "3/5 solved": `runs.repeat` + `check`, stop on failure.
- Existing VIs are **only dumped, never run**; only VIs the agent newly created under `write2\` are run (`must_runnable` in `lab/lablib.py`).
